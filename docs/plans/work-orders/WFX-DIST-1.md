## Objective

Make the prebuilt product reachable in one step on both desktop platforms.
Before this wave the repo produced CI workflow artifacts (deb + AppImage,
ubuntu lane only — `webflix-ubuntu-build.yml`, P9-LINUX-1 scope: "this
workflow creates no Release and no tag"); nothing was downloadable as a
release, and there was no Windows lane at all.

After this wave:

1. **A GitHub Release per tag** carrying `WebFlix-<version>-linux-amd64.deb`,
   `WebFlix-<version>-linux-x86_64.AppImage`, `WebFlix-<version>-win-x64.exe`
   (NSIS), each with a `.sha256` sidecar, plus `latest.json` (the
   install-script manifest) and the install scripts themselves.
2. **One-liner installs** (the zcode-distribution parity — see
   `scripts/zcode-distribution/installer.mjs`, the reference model in-tree):
   `curl -fsSL .../install.sh | sh` on Linux (deb via apt when available,
   AppImage into `~/.local/bin` otherwise, sha256-verified, no Node.js
   prerequisite — the app is a self-contained Electron bundle, unlike the
   zcode CLI which requires a host node) and
   `irm .../install.ps1 | iex` on Windows (download, SHA-256 verify, run
   the NSIS installer).
3. **Both lanes built in CI**: a `webflix-release.yml` pipeline —
   build-linux (ubuntu-24.04) + build-windows (windows-2025, the FIRST
   Windows lane in this fork) + a tag-gated release job.

## Why the Windows lane is expected to work (the survey)

The desktop packaging substrate is inherited from the zcode desktop, which
ships Windows:

- `electron-builder.config.js` carries the full `win`/`nsis` surface
  (`win.target: ["nsis"]`, assisted installer config, installer icons,
  `bundled-agents/${platform}/glm` extraResources driven by
  `getTargetPlatform()`), plus `patch-nsis-install-section.mjs` and the
  Windows native-search-tool chain (`scripts/native-search-tools-windows*`,
  win32-x64 ugrep/ripgrep plan enabled, archives shipped in-repo).
- The bundled agent (`zcode.cjs`) is platform-neutral JS
  (`prepare-agent-node-bundle.mjs`: "no native NAPI plugins… the same JS
  bundle is cross-platform universal", executed by Electron's own Node via
  `ELECTRON_RUN_AS_NODE`) — the platform key only names the staging
  directory.
- `node-pty` 1.1.0 ships win32-x64/arm64 prebuilds in the npm package
  (verified in-tree: `node_modules/node-pty/prebuilds/`); `koffi` embeds
  its Windows binaries in the package.
- `bundle.mjs --os win --arch x64` + `target-platform.mjs` normalize the
  win32 target; `ZCODE_SKIP_REMOTE_ASSETS=1` is the documented Windows-job
  practice (mock-cdn remote assets are not packaged).

## Non-goals (honest)

- **Windows runtime QA on-station**: the station is Linux-only; the
  Windows lane verifies build + artifact identity (PE ProductName,
  checksum, size). Runtime verification on a real Windows host is a
  recorded follow-up.
- **In-app auto-update**: stays fail-closed per the P8-RELEASE-DRIFT-1
  guard; publishing a Release creates NO update feed (`latest.json` is the
  install-script manifest, not an electron-updater feed; no token is ever
  passed to electron-builder; its publish config stays the inert localhost
  placeholder).
- macOS, rpm/pacman, arm64: unchanged scopes (frozen / runner-limited).
- No winget/Chocolatey/store distribution (submission processes, not repo
  machinery).

## Verification plan (real gates only)

1. Local: `dash -n install.sh` (POSIX parse), YAML parse of the workflow,
   the `latest.json` sed-parse contract pinned against a sample (the
   manifest format is generated by the release job and parsed by
   install.sh — both sides in-repo).
2. CI dry-run: `workflow_dispatch` the release workflow — both lanes must
   build green and upload workflow artifacts (the release job is tag-gated
   and skipped). Any Windows-lane finding is fixed BEFORE any tag exists.
3. Publish: tag `v3.14.3` (== package.json version, fail-closed checked by
   the release job) → the release job creates the GitHub Release with the
   full payload.
4. On-station end-to-end (the real "installable" proof):
   - `install.sh --appimage` against the live release: resolve → download
     → sha256 verify → install into `~/.local/bin` → LAUNCH the installed
     AppImage under Xvfb :99 → capture a real frame → clean kill.
   - Download all three artifacts + sidecars from the Release, verify
     checksums, `dpkg-deb` inspect the deb (identity fields), record
     sizes/sha256s.
   - install.ps1 cannot be executed on this station (no PowerShell) —
     recorded honestly; its logic is API-side testable only after a
     Windows host is available.
5. Evidence + WORKLOG + push.
