## 3. Per-user account ownership plan (flow, token boundary, why the cookie broker is not reusable)

**Recommended flow (reviewed, supported):**
- Primary: **OAuth 2.0 Authorization Code + PKCE** for installed/desktop apps — open the **system browser**, redirect to `http://127.0.0.1:{random-port}` loopback listener (custom URI scheme optional; manual copy/paste is deprecated). Per the official doc: `client_secret` is optional in the token exchange when PKCE is used, and DPoP is an optional hardening. Source: https://developers.google.com/identity/protocols/oauth2/native-app ("App redirect methods → Loopback IP address (macOS, Linux, Windows desktop)").
- Fallback (limited-input/TV/kiosk): **OAuth 2.0 device flow** (`oauth2.googleapis.com/device/code` + polling). Constraint: device flow supports **only** `https://www.googleapis.com/auth/youtube` and `https://www.googleapis.com/auth/youtube.readonly` (official "Allowed scopes" list). Using it for write actions grants the broad `youtube` scope instead of least-privilege `youtube.force-ssl` — acceptable only as an explicitly reviewed degrade.
- Scopes (least-privilege, incremental authorization per operation family): `youtube.readonly` (browse/read), `youtube.force-ssl` (subscriptions/playlists/comments/ratings/live chat writes), `youtube.upload` (uploads only), `yt-analytics.readonly` (creator analytics). Scope catalog: https://developers.google.com/identity/protocols/oauth2/scopes.
- **Operational prerequisites that gate onboarding:** (a) OAuth consent screen must be moved out of "Testing" publishing status — testing-status projects get refresh tokens that **expire in 7 days**; other revocation triggers: user revocation, 6 months unused, >100 live refresh tokens per account per client (official: https://developers.google.com/identity/protocols/oauth2 "Token expiration"); (b) sensitive-scope verification (unverified apps hit the 100-test-user cap and consent warnings) — https://support.google.com/cloud/answer/13463073; (c) all Google OAuth clients are additionally bound by the **Google API Services User Data Policy** (Limited Use: data only for prominent user-facing features in the requesting app; restricted transfers) — https://developers.google.com/terms/api-services-user-data-policy.

**Token boundary (per binding docs):**
- Tokens live in the Electron **main/host process behind an OS-backed credential vault adapter** (Keychain / Credential Manager / libsecret via Electron `safeStorage`), never renderer localStorage, logs, or Git (security-boundaries.md:29-37, repo:docs/architecture/security-boundaries.md). The inherited `credentialService` (encrypted JSON + cipher provider + file lock + corrupt-store refusal, repo:packages/services/src/credential/credentialService.ts:43-79) is the right interface shape but explicitly documents the safeStorage migration as future work (credentialService.ts:18-24) — adapt it behind a vault adapter; do not ship YouTube refresh tokens in the JSON store for the first slice if safeStorage is available.
- Connected-account record (provider, stable internal account ID, granted scopes, expiry, revocation state) per data-ownership.md:30-33; renderer receives account-safe status only.
- Disconnect must call `oauth2.googleapis.com/revoke` and clear vault state; never claim logout revokes provider tokens unless invoked and verified (security-boundaries.md:35).

**Why the inherited operator-cookie/CDP broker is NOT reusable as multi-user identity:**
1. **Single shared identity by construction**: the broker "Executes authenticated YouTube actions … by driving the logged-in YouTube browser tab over CDP. The operator's YouTube session lives in a logged-in browser on the lead sandbox (24/7 replay infrastructure)" (wfx20:mini-services/youtube-broker/README.md:3-7); the read path likewise injects one operator cookie jar from the `YT_COOKIES` env (wfx20:src/lib/youtube/session.ts:12-25). Every like/subscribe/comment from every end user would be attributed to the operator's channel — violating ADR-0003 decision §2 ("Each user connects their own account … no shared operator identity", repo:docs/adr/0003-youtube-first-per-user-identity.md:20), data-ownership.md:35 ("The old WebFlix 2.0 operator session is not an identity for desktop users"), and architecture-lock.md §2.11 (repo:docs/architecture/architecture-lock.md:28).
2. **Direct Developer-Policies violations**: API Clients "must not display or allow access to Authorized Data to anyone other than the authorizing user" (Developer Policies III.E.3) — a shared session inherently exposes one user's authorized data/actions to all users; actions must be "clearly initiated by the user" and tied to the authorizing channel (III.C / III.E.3). YouTube's ToS also prohibits accessing the service with automated means without written permission (youtube.com/t/terms, use restrictions).
3. **Not an authorization mechanism at all**: SAPISIDHASH cookie auth and CDP tab driving are reverse-engineered website-internal mechanisms (wfx20:src/lib/youtube-direct.ts:1-8; wfx20:mini-services/youtube-broker/cdp.ts:1-12) — AGENTS.md:95 and provider-policy-matrix.md:14 both prohibit shipping cookie replay/undocumented automation as an implicit fallback.
4. **Wrong shape for a desktop product**: one browser, one tab, one shared `BROKER_SECRET` over the network (wfx20:mini-services/youtube-broker/README.md:15-24) — a server-side singleton, not a per-profile local credential boundary; it cannot express per-user revocation, per-user quota attribution, or honest per-user error states.
