Status vocabulary: `supported` · `requires-auth` (needs a per-user OAuth grant) · `unsupported` (no official API exists for this scope — honest state, WebFlix-local substitute or user handoff only) · `blocked-by-policy` (out of scope by the work order / ADR-0003). The frozen §2.3 `CapabilityStatus` enum maps these onto UI states via the shell's honest-state vocabulary; `requires-auth` and `unsupported` are first-class frozen statuses on the Twitch manifest rows.

Quota/rate honesty: **the rate ledger is built from the AUTHORITATIVE provider response headers** — a point-based token bucket (official Helix API guide: separate buckets for app-access and user-access requests, the latter per client ID per user; default 1 point per endpoint request; the bucket window is 1 minute). Every Helix response carries `Ratelimit-Limit`, `Ratelimit-Remaining` and `Ratelimit-Reset` (Unix epoch seconds when the bucket refills), and the client ledger records that triple verbatim on every call. **No number is invented**: the frozen manifest quotas envelope carries the API guide's own documented example (`Ratelimit-Limit: 800`) with an explicit basis label (`TWITCH_RATE_LIMIT_BASIS`) — the actual bucket size is per client ID and is learned from the headers, never assumed. **No call is ever blocked pre-flight**: the provider's own HTTP 429 (with its `Ratelimit-Reset`) is the only authoritative enforcement; after one, the honest `rate-limited` capability/state is surfaced and nothing retries silently.

### The parent parameter — investigation result + integration note (the work order's explicit ask)

`parent` is the **hostname of the embedding page's origin** and is **REQUIRED**. Live-verified from this work order's sandbox (2026-10-11, every claim probed):

- **No parent → the player refuses to serve:** `GET https://player.twitch.tv/?channel=twitch` answers `HTTP 302 → /embed-error.html?errorCode=NoParent&content=player.twitch.tv%2F%3Fchannel%3Dtwitch`.
- **parent=localhost (the documented dev origin):** `HTTP 200`, `Content-Type: text/html` (193,519 bytes), and `Content-Security-Policy: frame-ancestors http://localhost:* https://localhost:*` — the player pins its framing allow-list to the declared parent (localhost parents get both schemes, any port).
- **parent=app.webflix.local (any declared hostname):** `HTTP 200` with `Content-Security-Policy: frame-ancestors https://app.webflix.local` — the parent value is echoed verbatim as the only allowed framing origin.
- Same player surface and same CSP behavior for the VOD path (`?video=1973304310&parent=localhost`).

**What this means for the desktop webview:** the player's CSP `frame-ancestors` must match the origin the desktop app's embedded webview loads its content from, or the frame is refused. **Dev time:** the documented localhost origin (`parent=localhost`) — live-verified above; `buildTwitchPlaybackPlan` validates parent as a bare hostname and REFUSES to build without one (`MissingTwitchParentError` — never a guessed origin), and the service watch bridge defaults to the dev origin explicitly. **Production-origin decision (integration note, deliberately NOT guessed in code):** the shipping desktop app must pin the webview's real content origin (a fixed app hostname or the custom-scheme origin host) and pass it as `parent` at integration time; that is an operator/integration step recorded here, per the work order's "do NOT guess silently" instruction. The `TWITCH_PLAYBACK_CONNECTOR` resolver-seam template carries the dev-time parent; the production integration replaces it.

## Rate-limit model and honest budget states (the header-authority row)

- **The headers are the authority.** Every Helix response carries `Ratelimit-Limit` (the bucket's max points), `Ratelimit-Remaining` (points left) and `Ratelimit-Reset` (Unix epoch seconds when the bucket refills) — the official API guide's own tracking mechanism. The client ledger (`helixApi.ts`) records that triple verbatim for every call (success AND error responses — the headers ride on both), and `getRateBudget()` exposes the last observed values plus `callsRecorded`, the explicit basis label (`TWITCH_RATE_LIMIT_BASIS`: "point-based token bucket per the official Helix API guide … the envelope figure is the guide's documented example (Ratelimit-Limit: 800), not a verified per-app value, and is never enforced pre-flight"), and `providerReportedRateLimit`.
- **The frozen manifest envelope carries the documented example** `{requestsPerWindow: 800, windowMs: 60_000}` — 800 is the API guide's own example header value (the actual bucket size is per client ID, with a separate user bucket per client ID per user); 60,000 ms is the guide's stated 1-minute bucket window. The precise model stays connector-local (MR-FD2 precedent).
- **No pre-flight blocking, proven:** a fixture test drives 5 consecutive calls through a served `Ratelimit-Remaining: 0` and all five reach the wire with `state: "ok"` — the connector never invents a ceiling from a (possibly stale) header reading. The provider's own enforcement is what acts.
- **HTTP 429 is the authoritative enforcement:** mapped to the typed `TwitchRateLimitedError` carrying the served `Ratelimit-Reset` epoch seconds, the budget flips to `provider-rate-limited`, the frozen capability maps to `rate-limited` — no silent retry, no degraded result presented as success.
- OAuth endpoints (authorize/token/revoke) are outside the media bucket; the embed player is player-side (no Helix call).
