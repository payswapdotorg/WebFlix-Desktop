# TikTok parity matrix — per-operation status, quota cost and user handoff

Owner: connectors lane (TIKTOK-CONNECT, Phase 3 opener). Reviewed against: docs/plans/work-orders/TIKTOK-CONNECT.md (scope rows 1–5), docs/plans/audits/AUDIT-SOURCES.md §5 (platform selection: TikTok #1) and the TikTok rows in docs/architecture/provider-policy-matrix.md, ADR-0003 (official surfaces only, per-user identity), contract-freeze §2 (binding shapes — TikTok is the second platform on the exact contracts YouTube uses), docs/plans/phase3-platform-selection.md (binding: TikTok first).

Status vocabulary: `supported` · `requires-auth` (needs a per-user Login Kit grant) · `unsupported` (no official API exists — honest state, WebFlix-local substitute or user handoff only) · `blocked-by-policy` (out of scope by the work order / ADR-0003). The frozen §2.3 `CapabilityStatus` enum maps these onto UI states via the shell's honest-state vocabulary; `requires-auth` and `unsupported` are first-class frozen statuses on the TikTok manifest rows (the frozen enum has no `region` status — regional unavailability maps onto `unavailable` with the regional explanation in `OperationCapability.detail`, and onto the frozen `unavailable{reason: "region"}` playback plan).

Quota/rate honesty: **TikTok publishes NO official rate-limit number for the Display API.** The ~600 req/min figure is a third-party report (AUDIT-SOURCES §5: "rate-limited (third-party reports ~600 req/min Display API — verify at integration)") and is UNVERIFIED. The frozen manifest quotas envelope carries it as the integrated-against approximation (`requestsPerWindow: 600, windowMs: 60_000`) and the client ledger tracks usage per rolling minute for observability — but **no call is ever blocked pre-flight on the unverified figure**. The provider's own signals (HTTP 429 with Retry-After, error envelope `rate_limit_exceeded`) are the only authoritative limits acted on; after one, the honest `rate-limited` capability/state is surfaced and nothing retries silently. oEmbed is a public endpoint with no documented per-caller quota.

## Rate-limit model and honest budget states (the UNVERIFIED caveat row)

- **No official number exists.** The ~600 req/min Display API figure is third-party-reported (AUDIT-SOURCES §5) and UNVERIFIED — no official doc states it and no observed response envelope has carried one. It is modeled as `TIKTOK_REPORTED_RATE_LIMIT_PER_MINUTE = 600` with the explicit basis label `TIKTOK_RATE_LIMIT_BASIS` ("third-party reports … UNVERIFIED; provider envelopes are authoritative").
- The frozen manifest quotas envelope carries the approximation `{requestsPerWindow: 600, windowMs: 60_000}` (the same envelope-approximation pattern YouTube uses; the precise model is connector-local — MR-FD2 precedent).
- The client ledger records every Display API attempt (`success | provider-error | rate-limited | network-error`) and `getRateBudget()` exposes `{state: ok | provider-rate-limited, usedInWindow, provisionalLimitPerMinute, basis, providerReportedRateLimit, retryAfterSeconds}` — **observability only**: a fixture test proves 5 calls through a `provisionalLimitPerMinute: 2` reference all reach the wire (NO invented ceiling).
- The provider's own signals are authoritative and degrading: HTTP 429 (with served Retry-After) or error envelope `rate_limit_exceeded` → typed `TikTokRateLimitedError` → honest `rate-limited` capability; no silent retry, no degraded result presented as success.
- oEmbed is a public endpoint with no documented per-caller quota; provider errors (including the regional redirect below) degrade honestly per-request.

## Regional availability (honest states, never silent)

TikTok is not served worldwide, and regional bans directly affect this connector's surfaces. Live-observed in this work order (2026-10-11, from the sandbox's Hong Kong egress IP — `ipinfo.io`: HK):

- `https://www.tiktok.com/oembed?url=…` → **HTTP 302 → `https://www.tiktok.com/hk/about`** (a regional marketing page, NOT the oEmbed payload); same result with a browser User-Agent. A followed fetch lands on the 200 `text/html` about page instead of JSON.
- `https://www.tiktok.com/embed/v2/<public id>` → the same **302 → `/hk/about`**.
- `https://open.tiktokapis.com` (Display API) is **NOT geo-redirected** from the same egress (the unauthenticated 401 envelope below was captured from HK).

Honest modeling, end to end: the geo-redirect signature (30x, or a followed 200 HTML landing where JSON was expected) surfaces as a typed `TikTokRegionUnavailableError` → frozen capability `unavailable` with the regional explanation (the frozen §2.3 enum has no region status) → playback `unavailable{reason: "region", recovery: change-region}` for observed-excluded viewer regions (`TIKTOK_OBSERVED_UNAVAILABLE_REGIONS`, connector-local — the frozen manifest cannot express exclusions; **TT-FD1**). The manifest `regions` list stays honestly empty (no positive served-region claim). Unknown regions are never guessed: they are probed at runtime and reported by the same typed error. Regional bans are a user-experience fact, so every affected path states it plainly rather than failing silently or rendering a marketing page.
