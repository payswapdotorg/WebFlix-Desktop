# Instagram parity matrix — per-operation status, quota basis and user handoff

Owner: connectors lane (INSTAGRAM-CONNECT, Phase 3 platform #3). Reviewed against: docs/plans/work-orders/INSTAGRAM-CONNECT.md (scope rows 1–5), docs/plans/audits/AUDIT-SOURCES.md §5 (platform selection: Instagram #3 — "high value but the browse/discovery parity users expect is largely unavailable officially"; the professional-accounts-only row), the Instagram intent rows in docs/plans/phase3-platform-selection.md, ADR-0003 (official surfaces only, per-user identity) and contract-freeze §2 (binding shapes — Instagram is the fourth platform on the exact contracts YouTube, TikTok and Twitch use).

Status vocabulary: `supported` · `requires-auth` (needs a per-user OAuth grant, or — for oEmbed — the operator's approved Meta app) · `unavailable` (the mechanism exists but cannot be driven by this app today — the honest watch-path default) · `unsupported` (no official API exists for this scope, or the surface is gated out of this connector's reach — honest state, WebFlix-local substitute or user handoff only) · `blocked-by-policy` (out of scope by the work order / ADR-0003). These map onto frozen §2.3 `CapabilityStatus` values on the manifest rows.

The design brief, verbatim from the audit: Instagram is **high value but the browse/discovery parity users expect is largely unavailable officially** — that unavailability is the deliverable. This connector is honesty-forward by construction: five authorized professional-account reads, three account-path rows, one honestly-unavailable watch row, and seventeen honestly-unsupported rows with official-status citations. No scraping, no private endpoints, no cookie replay, no invented discovery, and no scraping substitutes for removed discovery APIs.

## A. Shipped in Phase 3 — requires-auth reads (the professional-account surface)

All reads ride the **Instagram API with Facebook Login for Business** (host `graph.facebook.com`, version pinned to the live latest **v26.0** — the Graph API reference pages title themselves "Graph API Reference v26.0", and live probes on 2026-10-11 answered v25.0/v26.0 with the documented error envelope while v27.0 answered "Unknown path components"). Both official API variants are **professional-accounts-only** (Business/Creator); the Facebook Login variant additionally requires the professional account to be **linked to a Facebook Page**, and its Limitations section states it "cannot access Instagram consumer accounts". Consumer accounts are out of scope by the provider's own design, not by WebFlix's choice.

## B. Watch path — the investigation, the honest default, the pending approved row

The work order's mandate: _"investigate the official embed/oEmbed mechanism INCLUDING its app-review gate; if playback cannot be driven officially without approved credentials, emit honest unavailable + user-handoff (open official app) as the DEFAULT state and record the approved-credential path as the pending row. Do NOT force shapes; file IG-FD if a gap is structural."_

What the investigation found (live, 2026-10-11, HK egress — verbatim records in §Live-smoke):

1. **The official mechanism** is the oEmbed markup: a `blockquote.instagram-media` (with `data-instgrm-permalink`) plus the async loader `<script async src="//platform.instagram.com/en_US/embeds.js">`; the oEmbed guide documents that the loader "scans the page for the post HTML and generates the fully rendered post". The loader is also served at `https://www.instagram.com/embed.js` (live 200, `application/x-javascript`, 59,794 bytes).
2. **The oEmbed API live-answered an UNAUTHENTICATED request** for the guide's own example post (`https://www.instagram.com/p/fA9uwTtkSN/`) with HTTP 200 and the full payload (`type: "rich"`, `width: 658`, the complete `html` field — captured verbatim as the fixture `fixtures/instagram/oembed.success.json`). A dead shortcode, by contrast, answered the documented not-embeddable envelope (code 24, subcode 2207045, "Media Not Found … does not exist or you don't have permission to embed it"). Anonymous success on one public post is recorded as evidence, not treated as a waiver of the production gate.
3. **The embed page is conditionally frameable**: `https://www.instagram.com/p/<shortcode>/embed/` answers 200 anonymous with `x-frame-options: DENY` on direct navigation, but with **no x-frame-options** when the request carries iframe context (`Sec-Fetch-Dest: iframe` + cross-site `Referer`). The framing gate is request-context-driven — unlike Twitch's `parent` parameter, there is no query parameter WebFlix could pin. Whether a desktop webview navigating as a genuine embed iframe renders the player end-to-end **cannot be verified from this sandbox** without approved credentials and a packaged-app smoke.

The design that follows (no freeze deviation — everything folds onto the frozen §2.2 shapes; **no IG-FD needed** for the watch path):

| Operation        | Default state                                                                                                                                                                                                                                       | Approved-credential path (pending row)                                                |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `playback.embed` | `unavailable{requires-auth}` + `open-provider-app` handoff carrying the post permalink as the deep link — the work-order-mandated default; both builders are fixture-tested and the flag is the operator's integration step, never a silent default | `official-embed` plan against the documented embed page (`https://www.instagram.com/p | reel/<shortcode>/embed/`), built by `buildInstagramPlaybackPlan({embedApproved: true})`; the resolver adapter `INSTAGRAM_PLAYBACK_CONNECTOR`ships with`allowsEmbedding: false` and flips with the operator's post-review verification of iframe-context framing in the packaged webview |

**The operator gate chain — the heaviest of the four platforms, recorded in full (the work order's explicit ask):** a Meta **Business-type app** with the Instagram product and Facebook Login for Business configured → **App Review** approval for `instagram_basic`, `pages_show_list`, `pages_read_engagement`, `instagram_manage_insights` (and, for oEmbed reliance, the corresponding advanced access) → **business verification** where the review flow demands it → the app user must hold tasks on the Facebook Page linked to their Instagram professional account. Until this chain completes, every read row honestly renders requires-auth and the app access that exists is fixture-only. This is the same ruling class as the Google client ID (YOUTUBE-EXPAND) and the TikTok client key — but with strictly more links in the chain.

## Removed-API citations (the audit's verdict, checked against live evidence)

1. **Basic Display API — REMOVED, confirmed.** Changelog (verbatim): _"December 4, 2024 — The Instagram Basic Display API has been deprecated. All requests to the Instagram Basic Display API will return an error message."_ The developer docs page for the product now redirects to the Instagram Platform overview (probed 2026-10-11: `developers.facebook.com/docs/instagram-basic-display-api` → 301 → `developers.facebook.com/documentation/instagram-platform`). The connector records the removal as its own manifest row (`basic-display.profile`, unsupported with the citation) and routes own-profile/own-media reads through the current Instagram Platform APIs instead.
2. **Hashtag Search — the audit said removed; live docs say gated.** AUDIT-SOURCES §5 carries "hashtag search REMOVED (2024)"; the live Hashtag Search guide (probed 200 on 2026-10-11) still documents the full endpoint set behind App Review. Evidence over summaries: both facts are recorded on the `hashtags.search` row and here. Either way the consumer-facing conclusion is identical — no hashtag discovery in WebFlix — but the record does not pretend the API is gone when the provider still documents it.

## Rate-limit model and honest budget states

- **The official model is impressions-based, not a fixed ceiling.** The Graph API rate-limiting doc (Instagram Platform section, verbatim): _"Calls to the Instagram Platform endpoints, excluding messaging, are counted against the calling app's call count. An app's call count is unique for each app and app user pair, and is the number of calls the app has made in a rolling 24 hour window. It is calculated as follows: Calls within 24 hours = 4800 \* Number of Impressions."_ Impressions are "the number of times any content from the app user's Instagram professional account has entered a person's screen within the last 24 hours" — an account with zero impressions has **zero** API budget; there is no fixed hourly floor to promise anyone.
- **The envelope figure is the audit's UNVERIFIED approximation.** 4800/24 = 200 calls/hour at one impression — the "~200 calls/hour/account (third-party reports)" figure AUDIT-SOURCES carries. The manifest's `quotas` envelope models exactly this number with the basis label stating all of the above; it is never enforced client-side (the TikTok ~600 req/min precedent).
- **oEmbed has its own documented limit**: "You can make up to 1,000 requests every hour" (oEmbed guide, verbatim).
- **Business Discovery and Hashtag Search are subject to Platform Rate Limits instead** of the BUC bucket (rate-limiting doc, verbatim) — another reason the gated rows stay pending.
- **The authoritative runtime signals** are the provider's own `X-App-Usage` / `X-Business-Use-Case-Usage` response headers (JSON percentages: `call_count`, `total_cputime`, `total_time` over a rolling hour, served once an endpoint has seen enough traffic) and the provider's throttle errors. The client ledger records both headers **verbatim** when present, exposes the last observed values with the basis label, and NEVER blocks pre-flight: five straight fixture calls through "used" headers all complete; only the provider's own enforcement (HTTP 429 or the request-limit error codes) produces the honest rate-limited state, and it is never silently retried.
- **Throttle-error classification basis**: the rate-limiting doc confirms throttle errors exist; its error-code table fragment is client-rendered and did not extract from this sandbox (recorded honestly). The classifier matches the documented Graph request-limit vocabulary (codes 4/17/32 + HTTP 429), and an unmatched shape still surfaces as a typed `InstagramApiError` carrying the provider's own message — never swallowed.

## mediaKind honesty (frozen §2.1 mapping)

- `media_type VIDEO` + `media_product_type REELS` → **`short`** (the canonical short-form kind; the TikTok precedent).
- `media_type VIDEO` (feed video, or no product type reported) → **`video`**.
- `media_type IMAGE` → **dropped** — the frozen `MediaKind` enum is `video | short | live | podcast | audio | local-file`; it has no photo kind, and inventing one is a contract edit, not a mapping decision (the YouTube non-video-drop precedent). The service's drop report counts every dropped image so the UI can tell the truth about partial pages.
- `media_type CAROUSEL_ALBUM` → **dropped** — an album is a mixed photo/video container whose children each need a follow-up read; mapping it to any single kind would fabricate a watchable unit. Children reads are a later-phase option (§F-class), never guessed.
- Rows without a usable id → dropped; rows without a shortcode → mapped **without** an embed asset (no guessed token; the watch bridge honestly answers unsupported for them).
- No `AvailabilityFact` is ever fabricated — the own-media payload reports no per-item region availability (the TikTok discipline).

## Regional availability (honest states, never silent)

No positive served-region claim is made (`regions: []` on the manifest). Live-observed from the HK work-order sandbox (2026-10-11): `graph.facebook.com` answered every probe with the documented error envelopes (no regional gating observed); `www.instagram.com` served the homepage 200 anonymous while **profile pages 302-redirect to a login wall** (`https://www.instagram.com/accounts/login/…`) — an auth wall, not a regional block, and irrelevant to the API path either way. One reachable egress region is not a global claim.
